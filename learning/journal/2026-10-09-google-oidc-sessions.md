# Issue #19: Google OIDC Sign-in and Sessions

**Status:** Issue #19 implementation and final local security review complete. **Live Google OAuth has NOT been manually verified and must be tested before the Alpha release.**

## What changed and why

The Issue #18 persistence layer now has a narrow server-side admission path. A Google ID token is verified before the package-private `verifiedGoogleIdentity` value is constructed. The first user can become owner administrator only through a trusted local bootstrap invitation for that exact verified email. Other invitations never assign administrator status. The browser receives an opaque session cookie; PostgreSQL stores only its SHA-256 hash. Login attempts are short-lived and single-use with state, nonce, and PKCE. Logout requires an exact Origin and a session-derived CSRF token.

`cmd/lifeos-admin` is a deliberately local operator tool: explicit confirmation and a loopback PostgreSQL host are required. It is not an HTTP endpoint. `docs/AUTH_LOCAL_SETUP.md` holds the real Google setup procedure. The automated provider is a signed local test double, so it does not prove live Google configuration.

## Function-level Data Flow

| Step | Exact file/function; input → output; logic, next call, errors, tests |
| --- | --- |
| User Input | `apps/web/src/App.tsx` / `App`: clicking **Sign in with Google** follows `/api/v1/auth/start`; no credentials are entered into LifeOS. Next: browser GET. UI build checks rendering/types; the end-to-end server path is in `TestOIDCAndSessionIntegration`. |
| Frontend function | Sign-in is a plain anchor in `App` (**N/A function call**, because a browser navigation is required for Google redirects). After return, `App` calls `fetchCurrentUser`; sign-out calls `handleSignOut`. Errors show a short status. Web build/type checks cover these functions. |
| API request | Browser GET `/api/v1/auth/start`, then Google redirects to GET `/api/v1/auth/callback?state=…&code=…`. Next: `Auth.start` and `Auth.callback` in `internal/identity/auth.go`. Missing/mismatched/reused state returns 400; integration test checks both mismatch and replay. |
| Backend handler | `internal/identity/auth.go` / `Auth.start`: no input identity; generates state, nonce, PKCE verifier, inserts hashed attempt, sets HttpOnly state cookie, redirects to Google. `Auth.callback`: accepts state cookie/query and code; consumes attempt once, exchanges code with PKCE, verifies ID-token issuer/audience/signature/expiry, verified email, and nonce; constructs the private verified identity and calls `Auth.admitVerifiedIdentity`. Invalid provider proof returns 401; unavailable storage returns 503. Local signed-provider test covers invalid proofs. |
| Service | `internal/identity/auth.go` / `Auth.admitVerifiedIdentity`: verified `sub` and email → active LifeOS `User`. Resolves existing user by `sub`; only a new user uses verified email to locate a pending invitation. Calls repository functions below. Missing/revoked/expired invitation or inactive user denies access; database errors surface as unavailable. Integration test covers invited/uninvited/revoked/concurrent admission and admin boundary. |
| Repository | `internal/identity/repository.go` / `repository.findByGoogleSub`, `repository.findPendingInvitationByEmail`, `repository.acceptInvitation`: query unique `sub` binding or pending invitation; acceptance locks and atomically binds an internal user ID, Google `sub`, and invitation. Errors include unavailable invitation and uniqueness conflict; `TestIdentityMigrationAndRepository` and `TestOIDCAndSessionIntegration` cover them. |
| Database | `db/migrations/000002_identity_foundation.up.sql` owns `lifeos_users`, `google_identities`, `invitations`; `db/migrations/000003_auth_sessions.up.sql` owns `oidc_attempts` and `lifeos_sessions`. The latter stores state/token hashes, expiry, consumption/revocation timestamps and indexes. `internal/identity/auth.go` / `Auth.createSession` inserts the token hash; `Auth.currentUser` checks unexpired/unrevoked sessions and active users. The integration test migrates populated v2→v3 and tests session expiry/revocation. |
| Response | `Auth.callback` sets a random HttpOnly, SameSite=Lax session cookie (Secure on HTTPS) and 303 redirects only to the configured origin. `Auth.me` returns ID, email, admin flag, and CSRF token from an active session; 401 otherwise. `Auth.logout` calls `Auth.authorizeMutation` to check exact Origin, active session, and CSRF token, then revokes the stored hash, clears the cookie, and returns 204; 403 for CSRF failure. `Auth.RequireMutation` exposes that same guard to future write handlers and passes them only the verified `User`, never the session secret. `Auth.adminStatus` returns 204 only to the active owner administrator. Integration tests check redirects, disabled users, revoked sessions, and this guard. |
| UI update | `apps/web/src/api/auth.ts` / `fetchCurrentUser` gets `/api/v1/me` with same-origin cookies and returns `CurrentUser` or `null`; `App` shows signed-in email or invite-only sign-in. `App.handleSignOut` passes the CSRF token to `signOut`, then clears UI user state after a 204; failed requests leave the user state intact and show an error. `npm run web:build` verifies TypeScript; live browser/Google testing remains manual. |

## Operator flow

Trusted local terminal input → `cmd/lifeos-admin/main.go` / `run` checks `--confirm-local-operator`, action arguments, and literal loopback database host → `internal/identity/operator.go` / `NewLocalOperator` → `LocalOperator.Bootstrap`, `Invite`, or `Revoke` → package-private repository function → `invitations` table → prints only invitation ID/status. Invalid authorization exits before DB connection; repository checks active administrator for ordinary invite/revoke. `cmd/lifeos-admin/main_test.go` covers command confirmation and loopback checks; identity integration covers bootstrap and admin rules.
