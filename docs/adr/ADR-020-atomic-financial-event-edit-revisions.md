# ADR-020: Atomic FinancialEvent Edit and Internal Revisions

**Status:** Accepted — Product Owner approved ADR-020 and separately authorized local Issue #35 implementation on 2026-10-27. Final visual and financial-correctness review is required before commit, push or closure.

**Date:** 2026-10-27

**Issue:** [#35 Atomic Edit Transaction with Revision Audit](https://github.com/Faust217/LifeOS/issues/35)

## Context and retained decisions

Money currently creates a `FinancialEvent` with current `AccountMovement` and optional `CategoryAllocation` rows. Correcting a posted event requires separate Void and Create actions. The v9 schema has no event revision. A linked event can be Voided or Soft Deleted, and ADR-019 protects those writes with retained owner-scoped keys. An Edit must retain the event ID while correcting its current effects and retaining evidence of what changed.

Retain ADR-003's integer money and forward migrations, ADR-004's lightweight ledger and one-event Transfer, ADR-014's session-derived owner, ADR-016's distinct Void and Soft Delete, ADR-017's versioned normal exports, ADR-018's per-account opening anchors, and ADR-019's content-free committed replay. This decision does not supersede them. ADR-015 remains Proposed. Historical running balances remain Issue #36.

The current `repository.history` obtains event headers and then child rows in separate pool reads. That is insufficient once an Edit can replace children between queries. Export already uses one read-only `REPEATABLE READ` snapshot.

## Decision

### 1. One current ledger, one append-only audit snapshot table

Keep `financial_events`, `account_movements`, and `category_allocations` as the **only current effective ledger representation**. Edit the event root in place and update the current children inside one transaction. Existing balance, spending, History and normal export queries therefore continue to use current rows; they never join revision snapshots. The event ID, owner, kind, currency, creation time and posted status remain unchanged by Edit. Do not implement a second visible event, Void/Create pair, double-entry subsystem or general journal engine.

Forward migration v10 adds `financial_events.event_revision bigint NOT NULL DEFAULT 1 CHECK (event_revision > 0)` and one `financial_event_revisions` table. The table has `(owner_id, event_id, revision)` as primary key, a composite owner/event foreign key, `action` constrained to `legacy_baseline`, `create`, `edit`, `void`, `delete`, `recorded_at timestamptz NOT NULL`, optional `(owner_id, request_key)` foreign key to the retained v9 success marker, `snapshot_schema_version = 1`, and a non-null JSONB snapshot. A database guard rejects UPDATE/DELETE of audit rows; privileged migration repair remains a separately reviewed operation. No audit row is a movement or allocation for ordinary queries. Index only the owner/event/revision lookup needed to inspect or verify one event; avoid a global reporting index or new service.

Every snapshot is the **complete resulting state** at that revision, written in the same transaction as the current state. The schema-tagged snapshot contains event ID, kind, integer amount as a decimal string, currency, UTC occurred/created/voided/deleted instants, note, status and stored Void text; complete movement entries (`id`, `account_id`, integer amount string, currency, `created_at`); and complete allocation entries (`id`, `category_id`, kind, integer amount string, currency, `created_at`). Use deterministic child ID order. Row owner/action/revision/capture time and optional request key are audit metadata, not user-entered explanations. `recorded_at` is the database capture time, not a claimed physical commit time. Do not infer whether legacy Void text was user-authored. Snapshots contain private historic content, including after Soft Delete; retain them with the owner's internal ledger and backups, keep them out of ordinary APIs/exports/logs, and follow ADR-016's deletion/privacy explanation.

The current child row ID stays stable when the same account/category relationship is corrected, including an amount change. A changed account/category relationship removes its old **current** child and creates a new child ID; the old ID and complete values remain in the prior immutable snapshot. Never repurpose a child ID to mean a different account/category. The event ID stays stable. One Transfer continues to have exactly two opposite current movements, distinct accounts and no allocations. An empty allocation array remains explicitly Uncategorized. Voided and deleted events retain their current children internally, but their status/marker keeps them non-effective or hidden under existing rules.

On v10 creation, write revision 1. Each successful Edit, Void or first Soft Delete increments `event_revision` once and writes its new snapshot. An already-deleted Delete with a new key remains ADR-016's harmless 204 no-op: commit its idempotency marker, but neither increment the event revision nor add an audit snapshot. A matching old key returns ADR-019's content-free 200 receipt. Reject revision overflow atomically. No manual audit editing endpoint is in #35.

### 2. Narrow Edit rules and archived references

Only a session owner's posted, nondeleted expense, income or Transfer can be edited. The request is a **complete replacement** of editable fields: positive exact `amount_minor`, same-currency account relationship, UTC occurrence instant, note and, for income/expense, the entire allocation array. Event kind and currency must equal the current immutable values. The array may be empty for Uncategorized; if nonempty, category IDs are unique, kinds match and the exact positive allocation sum equals the new event amount. Transfer requests supply source and destination accounts only, with no allocations. No FX, event-kind conversion, unvoid, undelete, recurring transaction, or change to Goal links is added.

Allow an account/category already referenced by this event to remain referenced, including an edited amount, even when archived. This permits a historical correction without silently dropping a split. A newly introduced relationship must point to an active, same-owner account/category of the correct currency/kind. Removing an archived relationship is permitted; reintroducing it later while archived is a new selection and rejected. Validate all associations server-side. Preserve unchanged child IDs and all split values in the edit form; do not derive a full replacement from a paginated or partial history record.

Convert new local date/time input using the saved owner IANA timezone and the existing DST gap/overlap rules; send a frozen resolved UTC microsecond instant. An unchanged occurrence instant retains its exact stored UTC value. A timezone preference change never rewrites existing events.

### 3. Guarded read and write API

Add `GET /api/v1/events/{eventID}` for a complete owned visible event; a foreign, missing or Soft Deleted event returns 404. A Voided event may be read but is not editable. Return the current event DTO, complete movements/allocations, decimal-string `event_revision`, and strong `ETag: "<revision>"`, with `Cache-Control: no-store, private`. History DTOs also include `event_revision`. Read each event/history page and all its children from one consistent read-only `REPEATABLE READ` snapshot, or one equivalent SQL statement. Keep deterministic `occurred_at DESC, id DESC` pagination; this proposal does not provide snapshot-stable multi-request pagination or historical running balances.

Add `POST /api/v1/events/{eventID}/edit`, using `Auth.RequireMutation` plus the ADR-019 admission, key and final-session-revalidation path. Require one lowercase UUIDv4 `Idempotency-Key` and one strong, quoted decimal `If-Match: "<positive event_revision>"`; reject missing, weak, wildcard, duplicate, malformed, negative or overflowing revision values. The JSON body for income/expense is exactly `kind`, `currency`, `amount_minor`, `account_id`, `occurred_at`, `note`, and required `allocations` (possibly `[]`). The Transfer shape substitutes `from_account_id` and `to_account_id` for `account_id` and has **no** `allocations`. Reject unknown/duplicate JSON members, invalid UTF-8, trailing documents and bodies over 16 KiB. Use existing money/UUID/note/instant validation.

First successful Edit: `200 OK`, updated complete event DTO with incremented revision, matching `ETag`, `Idempotency-Replayed: false`, private/no-store. A committed matching-key replay returns exactly ADR-019's `200 {"outcome":"already_applied"}`, `Idempotency-Replayed: true`, private/no-store and **no old event DTO or ETag**. The client refreshes guarded reads. The same key with another target, operation, expected revision or normalized payload is `409 idempotency_key_conflict` without mutation.

For **new** Void/Delete commands after v10, require the same `If-Match` precondition, freeze it with the command and increment revision on actual status/marker change. This is required so a stale Void/Delete cannot silently act on a newly edited event. Preserve first success `204` and content-free committed replay. For a new-key Delete of an already-deleted owned event, retain ADR-016's 204 no-op even if the supplied revision is stale: it cannot change financial state. Foreign IDs stay 404. A Voided/Deleted event cannot be Edited; a Voided event cannot be Voided again. A stale revision of a still-visible event returns 412 before a new mutation.

The v10 cutover must continue to acknowledge retained v9 **v1** Void/Delete keys whose original requests had no `If-Match`. After authentication/Origin/CSRF and structural parsing, look up the owner/key and its stored fingerprint version first; compare a v1 marker with the unchanged v1 normalizer and original body, then return the receipt without current state checks. An uncommitted old-style request with no `If-Match` fails 428 and performs no write. A v2 key cannot be retried with a different/missing `If-Match`. Existing v1 create/account/transfer/opening contracts and their goldens remain unchanged. Do not run an old binary capable of unversioned Void/Delete writes against populated v10; coordinate the client/server cutover and settle in-flight requests.

Canonical v2 fingerprint is SHA-256 of Go `encoding/json.Marshal` of `["lifeos-finance-command-v2", canonical_owner_uuid, operation, canonical_event_uuid, parameters]`, with no unordered maps or transport/session fields. For Edit, `parameters` are:

- Income/expense: `[expected_revision, kind, currency, account_id, amount_minor, occurred_at, note, sorted_allocations]`.
- Transfer: `[expected_revision, "transfer", currency, from_account_id, to_account_id, amount_minor, occurred_at, note]`.
- Void: `[expected_revision, reason_mode, explicit_reason_or_null]`, retaining ADR-019's generated/explicit reason normalization.
- Delete: `[expected_revision]`.

Amounts and revisions are canonical decimal strings; UUIDs lowercase; currency uppercase; occurrence is canonical UTC microseconds; note bytes and whitespace are preserved; allocation pairs sort by canonical category ID and cannot repeat. Golden bytes/digests must lock these meanings. Store marker `operation='event.edit'` and `fingerprint_version=2` for Edit, and version 2 for new guarded Void/Delete; never rewrite v1 marker rows. A marker's stored version chooses its normalizer **before** replay/state checking; unsupported versions fail closed. Because v9 constrains the operation list, v10 must extend that check for `event.edit` without altering migration v9.

Use the existing `{ "error": { "code", "message" } }` envelope with privacy-safe text: malformed body/header 400 `invalid_input`; missing revision 428 `event_revision_required`; stale visible revision 412 `event_revision_conflict`; owned noneditable state 409 `event_not_editable` (deleted read/Edit remains 404); unknown/foreign event 404 `not_found`; archived new relationship 409 `archived_record`; invalid split/currency 400; unrepresentable final balance 422 `amount_overflow`; idempotency conflict/capacity/busy/unknown and session/Origin/CSRF errors retain ADR-019 codes. A definitive 4xx keeps the editable draft for review; an uncertain response keeps the exact frozen key, body, target, operation and `If-Match` for manual retry. Never auto-generate a second key to resolve uncertainty.

### 4. One atomic write and concurrency order

Extend `executeFinancialWrite` to choose the marker's fingerprint version and v2 command without weakening its eight-slot/10-second bounds, owner advisory lock, recheck, capacity or final session revalidation. For a **new** Edit, one READ COMMITTED transaction does: owner advisory lock → marker lookup/recheck/capacity/insert → owner-scoped event `FOR UPDATE` → expected revision and editable-state check → complete old child read → deduplicated union of old/new account row locks in ascending UUID order → sorted category locks/validation → exact current and replacement effect calculation → update current root/children, affected account `balance_revision`s, event revision and append-only snapshot → commit. No independent repository commit, processing marker or external queue. A rollback removes marker and all changes.

For every affected account compute its old eligible contribution and new eligible contribution independently using ADR-018: legacy includes all posted, nondeleted movements; anchored includes only those at/after its confirmed instant. Check `new_balance = current_balance - old_contribution + new_contribution` with PostgreSQL `numeric` or equivalent wide integer arithmetic, then require the **final** value fit int64. Do not reject a valid replacement because an intermediate subtraction/addition overflows int64. Keep ordinary negative balances allowed. Bump the balance revision of each affected old/new account, including a zero-current-effect pre-anchor leg, so a concurrent opening confirmation preview cannot silently survive changed history. Spending reads use only current posted, nondeleted allocations; pre-anchor expenses still count in spending. Transfer legs use their own account basis, never a combined-currency balance.

The owner advisory lock serializes covered writes of one owner. Row locks and the expected event revision decide different-key Edit/Edit, Edit/Void and Edit/Delete races: the first committed change wins; the later stale command gets 412 and no marker/effect. Same-key replay is recognized before revision/status checks. Account/archive/category operations outside ADR-019 still require their existing row-lock checks; integration tests must catch lock-order inversions. Any SQL/cancellation/overflow error rolls back current rows, audit snapshot, account revisions and marker together. No financial payload or prior snapshot is placed in access/error logs.

### 5. Populated v9 upgrade and export compatibility

Use **new forward migration v10** only. First add the revision column/table/append-only guard and extend the v9 operation constraint. Backfill one `legacy_baseline` revision-1 snapshot for **every existing v9 event**, including posted, Voided and Soft Deleted events, from its then-current root and complete children. Preserve every existing event/child ID, amount, relationship, status, timestamp, anchor, account balance revision and v9 marker. Record that this is a baseline captured at upgrade, **not** a reconstruction of prior edits, original pre-Void state, user-authored Void text or past commits. The migration must be transactionally consistent and tested with populated v9 data. No published v1–v9 file changes. A down migration refuses while events/audit revisions or v2 markers exist; a reviewed forward repair is the normal exit after populated use. Do not silently discard audit or retry protection.

Keep `lifeos-export-v1` and `lifeos-export-v2` JSON/Finance CSV schemas and golden fixtures unchanged. They already represent the **current** visible event and current child rows, including Voided and excluding Soft Deleted. Edit changes values within that documented current-state meaning; internal prior snapshots are not normal export rows, so #35 does **not** require v3. The v1 legacy-account restriction from ADR-018 remains. If a portable revision-audit export is requested later, define a separately versioned format and privacy review; do not append audit fields/rows to v1/v2. Export's existing single read-only repeatable-read snapshot remains mandatory under concurrent Edit.

### 6. User experience and acceptance gates

From compact date-grouped History, open a posted event's Edit action, fetch its complete current event/revision and prepopulate amount, exact UTC-derived owner-local date/time, note, account(s) and **every** allocation. Reuse a responsive sheet and existing saved-timezone/DST controls. Ordinary Save is one action with no extra confirmation. A 412 explains that the transaction changed and offers a fresh read while preserving the draft for comparison; never silently replace it. Validation and recoverable request errors also preserve drafts. The ADR-019 pending-command record must be versioned to include frozen `If-Match`; old v1 pending records must remain safely retryable, while unavailable/full/corrupt storage still blocks a new send. Voided and deleted events have no Edit action. Keep Void/Delete labels and behavior distinct. Audit/revision words need not appear in routine UI.

Implementation acceptance requires real guarded Go API and fresh disposable PostgreSQL tests for populated v9→v10/full chain/down refusal; create/Edit/Void/Delete snapshots and child IDs; amount/split/Uncategorized/Transfer/date/account corrections; archived references; exact anchor boundaries and mixed legacy/anchored legs; numeric limits and full rollback; same-key replay/lost response/process restart; stale races and lock timeouts; cross-owner/foreign references/session revocation/Origin/CSRF; History/Today/spending/export snapshot consistency and v1/v2 golden compatibility. Run full Go/vet, frontend tests/typecheck/build, OpenAPI lint/generated-contract checks, responsive 320px/390px/desktop and keyboard/focus tests, and `git diff --check`. Update actual function-level Mermaid flow, Codebase Map, Project State and English journal during separately authorized implementation. No personal database, deployment, #36 work, or automatic closure is authorized by this proposal.

## Concrete MYR examples

1. **Amount correction:** a posted MYR 10.00 cash expense leaves a recorded MYR 90.00 balance. Edit the same event to MYR 12.00. Its current movement becomes −MYR 12.00 and the balance MYR 88.00; revision 1 still records the original −MYR 10.00, but is never summed again. One event ID remains in History and normal export.
2. **Complete split:** a MYR 30.00 expense has Food MYR 20.00 and Medical MYR 10.00. Edit to MYR 35.00 with Food MYR 20.00 and Medical MYR 15.00. Both categories remain, their current allocation IDs stay associated with the same categories, spending totals change by the exact delta, and the revision-1 snapshot retains 20/10. Sending only Food or omitting the allocation array is rejected; sending `[]` explicitly changes the transaction to Uncategorized.
3. **Transfer across anchors:** Cash has a MYR 100.00 anchor at 10 October; Savings has a MYR 200.00 anchor at 20 October, with no other movements. A MYR 50.00 Cash→Savings Transfer dated 15 October leaves current Cash MYR 50.00 and Savings MYR 200.00 because Savings' leg is pre-anchor. Edit its occurrence to 21 October: the same event still has −50/+50 movements, Cash remains MYR 50.00, and Savings becomes MYR 250.00. Changing an endpoint instead applies that account's own anchor/currency rules; the prior transfer state remains audit-only.

## Alternatives considered and consequences

Revisioned movement/allocation rows in the current tables would require every balance, spending, History and export query to filter current revision correctly, and conflict with current per-event/account/category uniqueness constraints. A separate full double-entry journal is beyond the requested lightweight ledger. A single JSONB snapshot table plus current rows makes the old state durable with fewer query changes, at the cost of internally retaining multiple copies of sensitive historic contents. It is not a portable audit export or a promise of tamper-proof protection against a privileged database operator.

Leaving Void/Delete without revision preconditions allows a stale UI action to affect a newly edited amount, even with row locks. The v10 precondition cutover is therefore part of #35, while retained v1 keys retain their exact replay contract. Existing multi-request History pagination can still shift under concurrent writes; #35 fixes per-response header/child consistency but does not solve #36's snapshot-aware running-balance pagination.

## Acceptance and delivery boundary

The Product Owner approved all three decision points on 2026-10-27: internal full-state audit snapshots remain after Soft Delete and are omitted from normal export; new Void/Delete revision preconditions retain v1-key replay; normal current-state export v1/v2 does not require v3. Local Issue #35 implementation is separately authorized. Commit, push, closure, deployment, personal-data access and Issue #36 remain separately gated. A portable audit export or export v3 would require a new scope and review.
